A completed task should come with something you can inspect. Magistr keeps
the checks with the work: commands, output, exit codes, and the source inputs
those results belong to.

## Choose checks for the behavior

The game rules need checks for turns, occupied squares, winning lines, and a
draw. The opponent needs a stronger check: try every legal human reply and
make sure it cannot lose.

The Bevy board also needs to be opened and used. Keyboard input, readable
labels, and the rematch button are separate questions from whether minimax
returns a good move.

Use focused verification for bounded changes. Run the full configured suite
when requested or when a concrete risk calls for it. Project commands and
required custom gates live in `.magistr/project.json`.

## Read the actual result

Open **Checks** in the [recorded build](/#workflow). A command result includes
what ran and what it printed.

The opponent experiment initially failed because its assertion expected a
losing game for both marks. The corrected experiment found no loss when the
simple policy played first and a losing sequence when it played second.
Both attempts stay in the history.

A failed check is useful information. Diagnose the failure, correct its cause,
then rerun the affected checks.

## Review the interface separately

Try the actual controls. For the game, play a round with a pointer, play with
number keys, try an occupied square, and start another round.

Capture the interface at the sizes people will use. Open those images and
inspect the text, spacing, contrast, controls, and selected state.

Magistr records a written review separately from an executed command.
A screenshot file or a passing test does not establish that someone inspected
the screen.

## Check the current files

A result belongs to the inputs it checked. If those inputs change, an earlier
pass may no longer establish that the work is ready.

The recording includes a simple example: Cargo created the first lockfile
while the rules check ran. The tests passed, but completing the chunk was
refused because the inputs changed during the check. Running against the saved
lockfile produced current evidence.

That does not mean repeating everything after every edit. Rerun checks affected
by the change and keep the scope explicit.

## Run the full configured checks

When you want the full quality gate:

```sh
magistr validate
```

You can also use `$validate` in Codex or `/validate` in Claude Code.
This runs the configured standard and required custom checks.

## Ask for a useful finish

The final report should point to the finished change, the checks that actually
ran, the interface states reviewed, and any remaining limitation.

Then try the result yourself. The next thing you notice may become a small fix
or feedback for the [roadmap](/docs/roadmap#make-room-for-feedback).
