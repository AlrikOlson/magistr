Open your coding agent in the project you want to work on. That is where the
conversation happens: in Codex, Claude Code, or another agent connected to
Magistr. You can start with an empty folder or a project that already has years
of work in it.

Magistr keeps the parts of that work you will need again: the plan, the findings
behind a decision, the task in progress, and the results of its checks.

## Start with something you want to build

The [recorded example](/#workflow) builds tic-tac-toe in **Bevy 0.20.0**.
The brief is straightforward: play against the computer, see who won, then play
another round.

Even that little game raises useful questions. Who starts? Can a player click
twice? How good should the opponent be? What resets between rounds?

Talk through those questions with the agent. For an existing project, have it
read the code before suggesting a plan.

## Give the project a roadmap

Ask the agent to turn the result into pieces you can finish and check.
For the game, those pieces are:

1. Rules and turns.
2. A computer opponent.
3. A playable Bevy board.
4. Another round, with scores and alternating starters.

The opponent and board both need the rules. The final piece needs both of them.
Those are real dependencies, so the agent can tell what is ready to start.

Open **Roadmap** in the recording to inspect the actual pieces and their
acceptance criteria. [Planning a project](/docs/roadmap) explains how to keep
that plan useful as the project grows.

## Investigate the choices that matter

You do not need a research project for every line of code. You do need an answer
when the implementation depends on an assumption.

For the game, we tried a simple opponent: take a win, block a loss, then pick
the center or a corner. An experiment found a game it could lose when playing
second. That finding led to full search, followed by a check of every legal
human reply.

The [reasoning guide](/docs/reasoning) follows that decision. The recording keeps
the experiment and its output, so you can inspect the evidence yourself.

## Build one piece

Use `$next` in Codex or `/next` in Claude Code. The agent resumes interrupted
roadmap work first, or starts a ready chunk. It reads the requirements and
current code, plans the change, implements it, checks it, and commits it.

You can also ask directly for a bounded change. “Make the board usable with the
keyboard” is a useful request on its own. You do not need to rebuild the whole
roadmap to fix something small.

[Working in chunks](/docs/chunks) covers one chunk and longer runs.

## Use what you built

Play a round. Try clicking an occupied square. Play again and check the score.
A passing rules test cannot tell you whether the board is pleasant to use.

Ask the agent to save and inspect screenshots of the actual interface.
Keep useful feedback, investigate it, and change the plan when the findings
call for it. [Checking the work](/docs/verification) covers tests and visual review.

## Say how you want it delivered

Tell the agent whether you want a local commit, a pull request, a push to main,
or a deployment. Keep that instruction with the project.

For example:

> Once the relevant checks pass, commit and push directly to main.

At the end, you should get the change, the checks that ran, and any limitation
that still matters.

## Pick it up in a fresh session

Open the same project and ask the agent to read the saved work and current code.
It can find the unfinished piece, the decisions already made, and the checks
that need another run.

That is the part I wanted for my own projects: being able to keep going without
rebuilding the whole explanation in every chat.

[Saved work and sessions](/docs/concepts) explains what carries over.
