title: Working with Magistr
description: Start with something you want to build. Work out a plan, try the result, and keep making it better.

You can bring Magistr an idea you haven't worked out yet, a half-built app, or a
project you've been living in for months. Open your coding agent in that project
and start with what you want to do.

The part I enjoy is being able to take a project seriously: look at the whole
thing, ask difficult questions, and then actually work through the answers.
Magistr gives that work somewhere to stay.

## Look at the project together

Start by having the agent read what is there. For an existing project, try:

> Read the code and the saved plan. What's working, what's unfinished, and
> what would make the biggest difference? Explain what you find.

For a new project, describe who it's for and what you want to be able to do.
Let the agent ask questions. Talk through the awkward cases before they become
surprises halfway through the build.

When the answer needs research, ask for it. Have the agent keep the sources,
what it learned, and the decision you made. The [reasoning guide](/docs/reasoning)
shows how to make those findings useful next time.

## Turn the idea into a plan

A roadmap is the big picture. Break it into **chunks**: pieces of work with a
clear result and a way to check it. Give each one any dependencies it needs.

> Turn this into a roadmap. Put the important work first. Make each chunk
> small enough to finish and check, while keeping the whole project in view.

You can have several areas of work on the same roadmap. Focus on one, change
priorities, or revisit the whole thing when you learn something that changes
the project. [Planning a project](/docs/roadmap) covers that.

## Build something you can try

Use `$next` in Codex or `/next` in Claude Code. The agent resumes unfinished
roadmap work first, or takes the next ready chunk. It reads the current code,
does the work, runs the relevant checks, and commits the finished change.

You can also make a direct request:

> Fix the project picker. Check it with a long project name and a narrow
> window, and show me the result.

A small fix can stay small. You don't need to create a new roadmap every time
you notice a bug.

For a longer stretch, choose an area and a limit.
[Working in chunks](/docs/chunks) explains single chunks and runs that start
a fresh agent session for each piece.

## Try it, then say what you think

Use what was built. Read the change. Open the screens. Say what feels wrong,
even if you haven't worked out the exact fix.

> I can get through the flow, but I keep losing track of which project is
> selected. Look at it with real data and make that clearer.

The next iteration can change the plan as well as the code. Save feedback that
deserves a closer look, and investigate it before committing to a solution.

Tests help, and [checking the actual result](/docs/verification) matters too.
For an interface, ask the agent to save and inspect screenshots. A green test
doesn't tell you whether a menu is readable.

## Decide how the work gets delivered

Tell the agent how your project handles commits, reviews and publishing:

> After the relevant checks pass, commit and push directly to main.

That is one delivery policy; use the one you want for your project. At the end,
you should be able to find the change, what was checked, and anything left to do.

## Come back and keep going

In a fresh session, ask:

> Read the saved work and current code. Continue the unfinished task with
> the same scope and delivery instructions.

The next agent can read the roadmap, decisions, progress and check results.
It still needs to inspect the current files. [Saved work and sessions](/docs/concepts)
explains what carries over.

For a concrete example, [explore the recorded inbox build](/#workflow).
You can read its source changes, inspect its failed and passing checks,
and download the finished project.
