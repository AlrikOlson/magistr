A roadmap answers two everyday questions: what are we trying to build, and
what is the next useful piece?

Magistr keeps that plan in the project. Your connected agent reads and updates
it as the work changes.

## Start with a result

Describe something a person should be able to do. For the Bevy game:

> Play tic-tac-toe against the computer. Show the result, keep the score, and
> let me start another round.

That gives the agent something to plan around. For an existing game, have it
inspect the code first so the plan accounts for what already works.

## Break the work into chunks

A chunk is a deliverable with a finish you can recognize. “Rules and turns”
means legal moves, alternating marks, all eight winning lines, and a draw.
It is more useful than a box called “Backend.”

Each chunk keeps its title, description, acceptance criteria, priority,
dependencies, and status. It can also hold sections, notes, and a checklist.

The [recorded roadmap](/#workflow) has four pieces:

| Piece | What it needs first | What you get |
| --- | --- | --- |
| Rules and turns | Nothing | A board that rejects illegal moves and recognizes endings |
| Computer opponent | Rules and turns | An opponent checked against every legal human reply |
| Playable Bevy board | Rules and turns | A board you can use with a pointer or keyboard |
| Another round | Opponent and board | Scores, rematches, and alternating starters |

Open a piece in the walkthrough to read its actual requirements. The
connections show prerequisites. They are not a sequence of generic workflow stages.

## Separate priority from dependencies

Priority says which work matters most. A dependency says which work must be
finished first.

The board and opponent can both follow the rules. Making the opponent a higher
priority does not make it a prerequisite for drawing the board.

Magistr checks current prerequisites before starting a chunk. A pending item
can still be waiting for another piece; “planned” does not always mean “ready.”

## Keep larger areas together

Use workstreams for areas such as gameplay, level tools, or publishing. They
let you focus on part of a growing project while keeping the rest of the plan.

A chunk has its own detailed work plan when implementation starts. The roadmap
does not need a separate node for every file edit or test command.

## Change the plan when the facts change

Ask the agent to revisit a decision against the current code and research.
Then update the affected requirements and dependencies.

Use `$roadmap-refresh` in Codex or `/roadmap-refresh` in Claude Code to research
and revise the plan without starting implementation. Completed work stays
available as history. Work you no longer intend to build can be marked obsolete.

## Make room for feedback

Suppose the finished opponent feels too difficult. Save that observation as a
**signal** instead of interrupting the current task to invent a difficulty system.

A signal can keep the feedback, research, sources, and the findings that lead
to a decision. Useful work can become a linked roadmap chunk. You can also
dismiss the idea or leave it for later.

Use `$signals` or `/signals` to investigate saved feedback. Investigating it
does not itself start implementation.

## Start the next piece

Use `$next` or `/next` when you want implementation to begin. Name the
workstream if you want to stay in one area.

[Working in chunks](/docs/chunks) explains the work and checks behind a
completed roadmap item.
