A plan is Magistr's saved plan for a project: what to deliver, why it matters,
and what must happen first. Use a [connected agent](/docs/agents) to create or
revise it. Planning does not need to start implementation.

## Create a useful plan

In your agent conversation, describe the intended users, the result you want,
and constraints such as platform, budget, or delivery expectations. For an
existing project, ask the agent to inspect the code and saved work first.

> Review the existing project and propose a plan for the requested result.
> Save clear deliverables and acceptance criteria in Magistr. Explain the
> dependencies before starting implementation.

A **task** is one deliverable with a finish you can verify. Its record can hold
a description, acceptance criteria, priority, dependencies, notes, and a
checklist. Avoid tasks defined only by activity, such as “work on the backend.”

For example, in an application that imports contacts, a task could be “Import
a CSV file and report invalid rows.” Its criteria might cover a valid file, a
missing required column, and a row with an invalid email. The example assumes
the application already has a contact model.

## Set dependencies and priorities

A dependency means another task must finish first. Priority expresses which
eligible work matters most. Keep these separate.

If a report needs imported data, the import is a prerequisite. Changing the
report's priority cannot make missing data available. Ask the agent to check
for blocked or circular dependencies before selecting work.

Use **features** for larger areas, such as importing, reporting, and account
access. A feature groups deliverables; it is not a task list for a single
implementation.

## Read the saved plan

Ask the connected agent to summarize the plan, explain what is ready, and
show the requirements for a selected task. From a terminal in the project root:

```sh
magistr plan status
magistr plan next
```

The status command reports progress; the next command reports the next ready
task without starting implementation. Confirm that the saved requirements
match your intent before asking the agent to build.

If no task is ready, inspect unfinished prerequisites and scope filters.
Do not remove a real dependency just to make a task startable.

## Revise the plan

Use `$roadmap-refresh` in Codex or `/roadmap-refresh` in Claude Code to
research a topic and update the plan without implementing features.
Name the area to revisit and what has changed.

Keep completed work as history. Mark work obsolete when it is no longer
intended. Record why priorities, criteria, or dependencies changed so a later
session can understand the current plan.

Feedback can remain a [request](/docs/feedback) while it is being investigated.
Promote it into a task when the evidence supports a concrete deliverable.

## Begin implementation

Use `$next` or `/next` when you want one ready task implemented. The
`plan` skill also implements one task; its name does not mean
“planning only.” [Working in tasks](/docs/tasks) covers execution and bounded
runs.

Magistr's saved plan is authoritative. A generated Markdown view, when a
project permits one, is only a view. Projects with `plan_exports: false`
must keep the plan in Magistr and should not generate export files.
