# Concepts

Magistr keeps a project's roadmap, the sessions that work on it, their recorded work
and the checks that verify it. The desktop, command line and agent tools share the
project's state.

## Desktop

Open a configured project in `magistr-desktop`. The left side lists projects and
sessions; the conversation sits beside its working-copy details. **New session**
opens a separate conversation. Changing working copies keeps existing sessions
open. Return to a session to continue reading and recover your draft.

Write a message and press Return to send, or Shift Return for a new line. **Stop**
cancels the current turn and keeps your draft. Permission requests offer the
answers available for that action. **Copy conversation** copies its messages.
**Close session** ends that conversation; Quit closes the application and its
running work.

Choose System, Light or Dark under **Appearance**. Native text editing supports
selection, clipboard and input methods.

The current desktop focuses on conversations. Roadmap planning, detailed recorded
work, file review and project setup use the command line and agent tools.

## Roadmap

A work item has a title, status, priority, acceptance criteria and dependencies.
The next ready item is the most urgent pending item whose dependencies are done.
An item may be in backlog, pending, in progress, done, blocked or obsolete.

Use the connected agent to read the plan and request changes. `$next` or `/next`
resumes an interrupted item or starts one ready item, then stops. A planning request
does not start implementation. `magistr next` runs one item;
`magistr next-loop` continues up to its requested limit with fresh agent sessions.

## Sessions

Each session is one conversation with an agent in one working copy. Switching
sessions does not cancel their work. An unanswered request stays with the session
that asked it. Saved session history records its model, outcome, usage and recent
reply. Resume depends on the selected provider's support.

## Recorded work

The agent records an objective, its plan, actions and checks. It records findings
as work progresses, including the evidence, conclusion and next action.
Investigations keep related findings together, and later findings can correct
earlier ones. A step can be pinned so it stays easy to find. A checkpoint saves a
place in the work that can be restored. The connected tools read these records.

## Verification

A work item is done when its acceptance criteria hold and the selected checks pass.
Bounded changes use focused formatting, compilation, tests, lint and custom checks.
The complete suite runs when requested or when a change needs coverage across the
project. Each check records its command and real exit code. A failed required
check keeps the item from completing; diagnose it and rerun the affected checks.

## Project state

`magistr init` writes the project file and agent setup. Roadmap, reasoning and
execution records stay with the project under `.magistr/`; saved conversations
also use the configured local data folder. A fresh agent session recovers the
recorded plan and evidence before continuing.
