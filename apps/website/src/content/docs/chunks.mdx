A roadmap chunk is a piece of the project. The work plan beneath it explains
how the agent will deliver that piece.

For the game, “Computer opponent” is a chunk. Comparing a tactical policy,
implementing minimax, and checking legal replies are the work needed to finish it.
They do not need to become three separate roadmap projects.

## Finish one chunk

| Agent | Start one chunk |
| --- | --- |
| Codex | `$next` |
| Claude Code | `/next` |

The agent resumes interrupted roadmap work first. Otherwise, it starts a ready
chunk, reads its requirements and the current code, and plans the change.

The work keeps an objective, tasks, actions, checks, and artifacts such as
files or commits. Tasks can record progress without pretending the whole
chunk is already finished.

From a terminal:

```sh
magistr next
```

## Make the finish concrete

For the opponent, “done” meant that it returned legal moves for either mark
and could not lose against any legal human reply. A passing build alone would
not have established that.

Open **Work** or **Checks** in the [recording](/#workflow). You can follow the
task, read the experiment, and inspect the command that checked the opponent.

Required checks need current passing results before the roadmap piece can
be completed. The agent fixes failures and commits the finished change.

## Work through a longer run

Choose an area and a limit. To start a fresh Codex session for each chunk:

```sh
magistr next-loop --agent codex --max-iterations 5
```

Use `--agent claude` for Claude Code. Add `--track "Gameplay"` if that is
the workstream you want to work on.

The loop stops at its limit, when no work is ready in the chosen area, or when
it needs help to continue. Each session reads the saved work and current code.

Inside a chat, `$next-loop` or `/next-loop` finishes one chunk and prepares
a handoff. The terminal command manages the sequence of fresh sessions.

## Resume unfinished work

Ask the next session to read the saved objective, tasks, actions, and checks
before editing files.

If the opponent was implemented but its checks failed, that is where the work
should resume. A fresh chat should not silently start a different roadmap item.

Earlier passes may need another run when relevant files have changed.
[Checking the work](/docs/verification) covers that.

## Keep small requests small

A direct request can use a focused plan without becoming a roadmap chunk.
A copy correction, a review, or a small bug fix should stay proportionate to
the work.

Keep your commit, push, and publishing instructions with the project so they
apply across sessions and longer runs.
